# データ基盤の学習チェックリスト

作成日: 2026-09-09

このラボの調査から導かれた，**データ基盤を設計するために埋めておく項目**の一覧．
カタログツールの比較そのものではなく，その前提になる知識を扱う．

## なぜこれが必要か

`plans/002-issue1-datalake-example.md` の 2.9(c) で出た結論による．

> カタログが自動で取れるのはスキーマの収集と，条件が揃ったときのリネージまでで，
> 意味づけは原則として人間が入れる．その「条件」を握っているのは基盤側の作り．

つまり **カタログの価値は基盤の作りに従属する**．基盤の形が決まらないうちに
カタログを選ぶと，選定の前提の方が後から動く．

## 現在地

**習得済み**: MinIO / メダリオンアーキテクチャ / Python + polars

**学習予定**: Iceberg / DuckDB / dbt / Dagster

ただしこの 4 つは決定の重さが違う．

| | 何を決めるか | 重さ |
| --- | --- | --- |
| Iceberg | 「何をテーブルと呼ぶか」．ストレージ層の形 | 重い．後から変えるとデータの置き直しになる |
| 変換を SQL で書くか Python で書くか | **メタデータが自動で出るかどうか**（計画 2.6 の 3 経路） | 最重要の分岐．dbt を採るか以前の問題 |
| Dagster | 実行と資産の管理．Python 変換でも自動リネージが取れる経路 | 中．変換言語の決定に従属する |
| DuckDB | 実行エンジン | 軽い．計画 2.6 の通り，入れてもリネージは自動にならない |

## チェックリスト

### A. まず埋める

- [ ] **取り込み（EL）と冪等性** — メダリオンは bronze から先しか教えない．実装が一番つらいのは入り口
  - [ ] 差分取り込みの方式（全量スナップショット / 更新時刻ウォーターマーク / CDC）と，それぞれの破綻条件
  - [ ] 冪等性 — 同じジョブを 2 回流して二重にならないか．失敗した日だけ流し直せるか
  - [ ] 遅れて届くデータ（late arriving）とバックフィルの設計
  - [ ] ツール: dlt（dlthub．polars / Python と相性が良い），CDC なら Debezium
- [ ] **テーブル / ファイル設計の実務** — 運用で最初に壊れる場所
  - [ ] small file problem．パーティション粒度の決め方
  - [ ] ファイルサイズ，row group，圧縮，ソート順の効き方
  - [ ] Iceberg の運用: compaction，スナップショットの期限切れ，orphan file の掃除
        （**「Iceberg にすれば楽」ではなくメンテナンスジョブが増える**．学習項目として最初から数える）
- [ ] **データ品質のテスト** — 計画 2.4 の名寄せの正しさを担保できるのはここだけ．リネージは「繋がっている」しか言わない
  - [ ] ツール: Pandera（polars 対応，Python で完結）/ dbt test / Great Expectations / Soda
  - [ ] スキーマ変更をどう受け入れるかの方針（データ契約）．
        計画 2.5 のスキーマ変更履歴は**検知**であって**防止**ではない

### B. gold 層で必ずぶつかる

- [ ] **ディメンショナルモデリング** — メダリオンは「層」を教えるが「gold をどう作るか」は教えない．
      空白のままだと gold が用途ごとの謎テーブル置き場になる
  - [ ] Kimball のスタースキーマ，ファクトとディメンション
  - [ ] SCD Type 2（履歴を持つマスタ）とサロゲートキー
  - [ ] grain（1 行が何を表すか）を最初に決める習慣
- [ ] **サービング層 — 誰がどうやって読むか**．これを決めないと Iceberg もカタログも選べない
  - [ ] 単一ノードで足りるなら DuckDB で完結．複数人 / BI から叩くなら Trino．集計特化なら ClickHouse / StarRocks
  - [ ] BI: Metabase / Superset
  - [ ] 計画 2.8 と直結 — Iceberg を採って OpenMetadata も使う場合の抜け道が Trino

### C. Iceberg とセットで

- [ ] **Iceberg カタログの選定**（Lakekeeper / Apache Polaris / Nessie / Gravitino / AWS Glue）．
      Iceberg 本体だけでは動かせない
- [ ] 用語の衝突に注意

| 語 | 意味 |
| --- | --- |
| Iceberg カタログ | テーブルの現在のメタデータの場所を管理する．**機械が読む** |
| データカタログ（OpenMetadata / DataHub） | 人間が意味・所有者・リネージを見る．**人が読む** |

### D. 運用で後から効く

- [ ] **アクセス制御と秘匿情報** — MinIO のポリシー（prefix 単位）とテーブル単位の権限は粒度が違う．
      PII をどの層まで入れるか，マスキングをどこでやるか．
      **カタログのタグは印であって，強制力は実行エンジン側にある**
- [ ] **可観測性** — 鮮度（freshness）・件数の異常・スキーマドリフトの監視．
      リネージより先にこれが無いと事故に気づけない
- [ ] シークレット管理と IaC

## 今は学ばなくてよいもの

**Spark / Kafka / Flink / Kubernetes**．polars + 単一ノードで足りているうちは不要．
「モダンデータスタックを一通り」は終わらない．

必要になる条件は次の 3 つだけ．

1. メモリに乗らないデータ量になった
2. 秒〜分単位の鮮度が業務要件になった
3. 複数チームが同じテーブルに同時書き込みする

3 は分散処理ではなく Iceberg が解決する領域なので，Iceberg の学習でカバーされる．

## 学習の順序

1. 取り込みと冪等性
2. テーブル / ファイル設計（Iceberg と同時）
3. ディメンショナルモデリング
4. データ品質のテスト
5. サービング層
6. 可観測性・権限

dbt / Dagster は「変換を SQL で書くか Python で書くか」を決めた後で，
答えに応じてどちらかに寄せる．1〜3 がその判断材料になる．
